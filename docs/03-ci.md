# CI 验证范围

共享来源为 [CI 模板](../templates/workflows/ci.yml)和[变更分类 action](../templates/actions/changes/action.yml)，由 sync-repo.sh 同步到各库。平台、文档和包元信息的分类在同一处维护，仓库专属工作流消费这些结果。

## 变更与验证

| 改动 | 原生验证 |
|---|---|
| ios、example/ios、Podspec、example Gemfile | iOS |
| android、example/android | Android |
| 公共源码、公共 example、依赖、锁文件及共享构建配置 | iOS 和 Android |
| 普通文档、站点内容、普通 JS 测试及已识别的纯工程校验脚本 | 不启动原生构建；执行所属文档、测试或工程检查 |
| package.json 或 example/package.json 仅修改 description、keywords、homepage、bugs、repository、author、contributors、funding | 文档／元信息相关验证 |
| 包的 scripts、依赖、版本、导出、Codegen 或其他字段变化 | 共享运行输入，验证双端 |

包比较使用 PR 的 merge base、push 前后提交或 merge_group 的基准与目标提交。解析失败、提交不可取得或未知输入按共享运行输入处理。未知工程脚本仍保守验证双端，确认其消费者后才缩小范围。

## 标准作业

| 作业 | 责任 |
|---|---|
| changes | 完整 Git 历史、共享路径分类、包字段比较与 website 存在检测 |
| actionlint | 始终检查 changes 成功，再校验 workflow 与 shell |
| lint、test | 相关代码的 Lint、类型及完整库 coverage |
| build-library | 公共 JS／TS 或共享运行输入变化后的包构建 |
| build-android、build-ios | 对应平台或共享运行输入变化后的原生构建与专属验收 |
| website | 实际文档站输入变化后的 LLM 生成测试、类型检查及站点构建 |

标准 CI 在 main push、PR 和 merge_group 上运行，不在 workflow 顶层用 paths 隐藏 required checks；按 job 条件选择重任务。changes 失败由已有 required actionlint 明确阻止放行，不能仅依靠其他依赖作业 skipped。

## 仓库专属验证

需要原生额外验收的仓库，在 .github/ci/android.sh 或 .github/ci/ios.sh 维护实际检查。标准原生 job 构建后执行对应脚本，脚本失败即该 required job 失败。脚本存在时，即使 Turbo 缓存命中，也准备 JDK／SDK 或 Xcode／Pods，不能假设缓存恢复了生成文件。

Umeng 的 native contract、XCTest、Android 单测／混淆 Release Manifest 及 Codegen provider 检查在此接线。独立 consumer、example 和文档契约验证保留在 Project Validation；PR 标题编辑只触发必要的发布级别检查，正文编辑不重新启动重任务。

Design 的 showcase 保留真实资料校验和独立 example 测试。普通相关文档只校验当前资料；校验器及其测试变化才执行校验器回归。库 Lint、类型、coverage 与包构建由标准 CI 承担，避免在 showcase 中重复执行。

## 缓存、原生格式与定期检查

Yarn 只缓存下载包，每个需要依赖的 job 正常执行 immutable install。Turbo 按平台和锁文件恢复缓存，新提交另存；Gradle 缓存包含 wrapper 配置。实际版本、命令、缓存键和工具前置以模板为准。

Native Lint 的 lint-cpp／lint-kotlin 继续作为原生库必需格式检查。RN-next Build Check 是独立的定期／手动兼容性检查；PR 修改该工作流时只验证检测步骤，不启动 next 双端构建。

## 维护与验证

修改共享规则后，运行 ci-template.test.sh、ci-filter-contract.test.mjs 和包比较回归，并同步实际消费者。定向回归应覆盖单平台、公共输入、纯文档、测试文件、元信息、比较失败及原生专属检查前置。同步后保留各库确有用途的专属验收，按实际提交核对 CI。

必需检查名称与远端 ruleset 保持一致；仓库专属汇总不能假定另一 workflow 已成功。远端规则维护见[分支保护](05-branch-protection.md)，分发方式见[同步说明](13-sync.md)。
